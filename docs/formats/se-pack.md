# `se.pack` — runtime SE cache format

OpenRecet ships **no game audio**. The 110 sound-effect (SE) WAVs that
the original engine embeds as PE resources are instead extracted from the
user's own retail `recettear.exe` on first run and cached in a single
`se.pack` file. Subsequent runs load straight from the cache.

This is the container for that cache. It is produced and consumed only by
`src/se_pack.c`; it is never committed and never redistributed (it
contains proprietary audio derived from the user's own copy).

## Why a cache at all

Extraction walks the retail exe's `.rsrc` (custom resource type `WAVE`,
keyed by the id table at VA `0x005d1584` — see `audio_se_names.c` and
`engine-quirks.md` #46). That requires the retail exe to be present and a
`LoadLibraryEx` map of a 5.6 MB file. Caching the 110 blobs in one packed
file makes every run after the first independent of that, and lets us key
on the retail-exe hash so a game update transparently re-extracts.

## Location

`%LOCALAPPDATA%\openrecet\se.pack` (e.g.
`C:\Users\<you>\AppData\Local\openrecet\se.pack`). Kept out of the
Recettear install dir on purpose, so the game folder stays pristine and
the cache survives a game reinstall.

## Layout

All integers are little-endian. Offsets are from the start of the file.

```
offset  size            field
------  --------------  -----------------------------------------------
0       8               magic         = "OPRSEPK1" (no NUL terminator)
8       4   u32         version       = 1
12      4   u32         count         = slot count (110 = AUDIO_SE_COUNT)
16      32  u8[32]      retail_sha256 = sha256 of the recettear.exe this
                                        cache was extracted from
48      count*8         entry table   (one 8-byte entry per slot, in
                                        slot order):
            +0  u32     blob_offset   = file offset of this slot's WAV
                                        bytes, or 0 if the slot is absent
            +4  u32     blob_size     = byte length, or 0 if absent
48+count*8  ...         blob region   = the WAV blobs, concatenated in
                                        slot order (absent slots emit no
                                        bytes)
```

`count` is fixed at 110 for this game, but is stored so the reader can
reject a pack built for a different SE table.

## Absent slots

Slot 2 (id `0x0135`) is listed in the engine's SE id table but has **no
`WAVE` resource** in the shipped exe — `FindResource` returns NULL.
Such slots are written with `blob_offset = 0` and `blob_size = 0`, and
the loader leaves the corresponding DirectMusic segment NULL (so
`audio_play_se(2)` silently no-ops, matching the engine). Any future slot
that the retail exe also lacks is handled the same way.

## Validity / invalidation

On startup the loader:

1. Locates the retail exe (`OPENRECET_RETAIL_EXE`, else `recettear.exe`
   in the working directory — the game dir).
2. Computes its sha256.
3. If `se.pack` exists, parses it and compares `retail_sha256` to the
   freshly computed hash **and** `count` to `AUDIO_SE_COUNT`.
   - match → use the cache as-is.
   - mismatch / missing / corrupt / wrong magic-or-version → re-extract
     from the retail exe and overwrite the cache.

This means a Recettear update (new exe hash) automatically triggers a
re-extract; no manual cache busting.

## Relationship to the old build-time embedding

Before the public-release detour, the SE WAVs were linked into
`openrecet.exe` itself (`src/se.rc` → `se.res.o`, generated by
`tools/extract/se-rc.py`). That embedded proprietary audio in our binary,
which blocked publishing a build. The build-time path is retired; the
`tools/extract/se-wavs.py` extractor is kept as a dev/reference tool. The
C extractor in `src/se_pack.c` is the runtime port of that same `.rsrc`
walk, except it reads the **packed** retail exe directly (SteamStub
leaves `.rsrc` unencrypted — see `docs/reference/vendor-exe.md`).
